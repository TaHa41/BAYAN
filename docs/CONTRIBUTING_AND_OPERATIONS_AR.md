# دليل فهم BAYAN والعمل عليه بأمان

هذا الدليل موجّه لأي مطوّر أو وكيل ذكاء اصطناعي أو مساهم جديد. اقرأه قبل تغيير الكود.

2. [المرجع الرئيسي](MASTER_PROJECT_REFERENCE_AR.md) — متطلبات المنتج وحالتها والقرارات والقيود.

## كيف نفهم النظام؟
- المستودع GitHub هو مصدر الحقيقة للكود والتغييرات؛ لا تفترض أن تقريرًا أو محادثة تعكس الكود الحالي.
- الإنتاج هو Worker على Cloudflare، وقاعدة البيانات D1؛ تحقق من إعدادات المشروع والـbindings الفعلية قبل تغيير أي مورد.
- GitHub Actions هو مسار الاختبار والنشر. افحص ملفات workflow وسجل التشغيل للـcommit نفسه.
- افصل بين: الكود موجود، الاختبارات ناجحة، النشر اكتمل، والإنتاج جرى اختباره. هذه أربع حالات مختلفة.
- للبحث والأخبار والمقالات والصور والفهرسة، راجع ملفات التنفيذ والاختبارات الحالية قبل تعديل السلوك؛ لا تنشئ مسارًا موازيًا أو مصدر بيانات بديلًا دون مبرر موثق.

## قواعد إلزامية لكل تغيير
1. افتح Issue أو Pull Request يوضح المشكلة أو الهدف.
2. اكتب في وصف PR: المشكلة/الدليل، السبب المثبت أو ما لم يثبت، التغيير، الاختبارات، المخاطر، التراجع، وأثره على الإنتاج.
3. أضف أو حدّث الاختبارات التي تمنع رجوع المشكلة. لا تكتفِ بتعديل الكود.
4. حدّث المرجع الرئيسي إذا تغير مطلب أو قرار أو حالة ميزة، والخط الزمني عند وقوع حادثة أو قرار مهم.
5. سجل التغييرات المدمجة على main يُحدّث تلقائيًا بواسطة workflow؛ لا تعدّل سجل commits يدويًا إلا لتصحيح خطأ موثق.
6. لا تضع مفاتيح API أو كلمات مرور أو رموز جلسات أو بيانات شخصية في الكود أو التوثيق أو سجلات CI.
7. لا تحذف بيانات أو migrations مطبقة، ولا تغيّر بنية البيانات أو موارد Cloudflare الإنتاجية دون خطة واضحة ومراجعة وموافقة صريحة.
8. لا تخفّض شروط التحقق أو متطلبات خمسة ناشرين مستقلين للمقالات الموثقة لمجرد تجاوز فشل الاختبار.
9. لا تدّعِ أن النشر أو الإصلاح نجح دون رابط تشغيل/اختبار وSHA مطابق للإنتاج.
10. إذا تعذّر الوصول إلى مورد أو سجل، اذكر القيد كما هو ولا تخمّن النتيجة.

## قبل الدمج
- [ ] CI ناجح على SHA الخاص بطلب الدمج.
- [ ] الاختبارات الحالية واختبارات الانحدار ناجحة.
- [ ] التغيير لا يزيل ميزة مطلوبة بصمت.
- [ ] لا أسرار أو بيانات حساسة في diff.
- [ ] حدود الحصص والتكلفة ووقت CPU والمهلات واضحة.
- [ ] التوثيق يعكس ما تغيّر فعلًا.
- [ ] لا توجد تغييرات مدمرة أو migrations غير قابلة للتراجع دون موافقة.

## بعد الدمج والنشر
- [ ] سجّل SHA المدموج وSHA المنشور.
- [ ] تحقق من أن SHA الإنتاج يطابق المقصود.
- [ ] نفّذ smoke tests للمسارات المتأثرة.
- [ ] افحص سجلات الأخطاء والحصص عند الحاجة.
- [ ] حدّث حالة الميزة في المرجع الرئيسي: مؤكدة، جزئية، مفتوحة، أو تحتاج تحققًا.
- [ ] إذا فشل أي تحقق، افتح متابعة ولا تعلن اكتمال الإصلاح.

## حدود السجل التلقائي
الـworkflow يسجل commits التي تصل إلى `main` وتاريخها ورسائلها والملفات المتغيرة. لا يستطيع استنتاج النية أو السبب الحقيقي أو صحة الإنتاج من diff وحده؛ لذلك يجب أن يحتوي PR على شرح بشري واضح وأن تُحدّث حالة البنود في المرجع الرئيسي. لا تسجّل محادثات أو أسرار أو تفاصيل غير موجودة في GitHub تلقائيًا.

## كيف تمنع تكرار خطأ؟
حوّل كل حادثة إلى: (1) خطوات إعادة إنتاج، (2) سبب مثبت، (3) اختبار انحدار، (4) إصلاح صغير، (5) CI، (6) نشر بنفس SHA، (7) تحقق إنتاجي، (8) توثيق الدليل. لا تغلق الحادثة قبل الخطوة الأخيرة.
